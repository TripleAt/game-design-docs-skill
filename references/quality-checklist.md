# Game design document quality checklist

## 読者と目的

- [ ] 誰が読む文書か分かる
- [ ] この文書で何を判断・実装・検証するか分かる
- [ ] 企画の状態が Draft / Review / Approved などで示されている

## 読者と判断

- [ ] 主な読者が明記されている
- [ ] 読後に決めてほしいことが一文で分かる
- [ ] 読者が知りたい疑問（面白さ、価値、制作条件、リスク）が洗い出されている
- [ ] 価格・プレイ時間・予算・期間・チームなど、判断に必要な制約がある

## 初心者向け最小構成

- [ ] 表紙にタイトル、ジャンル、想定プラットフォームがある
- [ ] 企画意図とコンセプトが分かれる
- [ ] ターゲットが具体的なプレイヤー像になっている
- [ ] プレイヤーの立場、目的、背景がある
- [ ] 画面で見える情報とプラットフォームに合った操作方法がある
- [ ] ゲームシステムとゲームサイクルが説明されている
- [ ] 画面ラフや操作フローなど、必要な図解がある

## 体験

- [ ] 一行のプレイヤー約束がある
- [ ] プレイヤーの状況、動機、対象プラットフォームがある
- [ ] 形容詞ではなくプレイヤーの行動と結果で説明されている
- [ ] 企画の柱が3つ以内で、約束に結び付いている

## コンセプト

- [ ] 「どんなゲームだから、どう面白い」が一文で説明できる
- [ ] UXが1〜3個に絞られている
- [ ] 映画・小説ではなくゲームで作る理由がある
- [ ] 既存ゲームとの差分と最初のフックがある
- [ ] 「人気になる」などの結果目標がコンセプトと混ざっていない
- [ ] 仕様の採否をコンセプトの判断軸で説明できる

## ループとシステム

- [ ] コアループが状況から次の判断までつながっている
- [ ] ループ内に意味のある選択とトレードオフがある
- [ ] 成功、失敗、再試行の扱いがある
- [ ] 主要システムの入力、状態、出力、例外が分かる
- [ ] システムごとに「ルール → 挑戦・選択 → UX」がつながっている
- [ ] ジレンマ、ダイナミクス、不確定性の採否理由がある
- [ ] 資源ごとに獲得方法と消費先がある

## ゲームサイクル

- [ ] ゲーム要素がプレイヤーの「○○したい」という動機の矢印でつながっている
- [ ] サイクルの入口、終着点 / 辞めどきが分かる
- [ ] 動機が次に移る根拠（報酬、情報、変化、目標）がある
- [ ] 耐久度の仕組みがコンセプトと対象プレイヤーに合っている
- [ ] 水増しではなく、適切なプレイ時間として説明できる

## スコープと制作

- [ ] MVPがプレイヤー約束を証明する最小範囲になっている
- [ ] 非目標が明記されている
- [ ] チーム、期間、対象環境の仮定がある
- [ ] 予算、価格・価値、完成させる根拠がある
- [ ] 技術リスクが検証方法付きで列挙されている

## 検証と不確実性

- [ ] 事実、仮説、決定、未決定が区別されている
- [ ] 重要な仮説に観測方法がある
- [ ] 成功基準が観測可能である
- [ ] 未決定事項に担当と期限、または次の確認がある
- [ ] 競合・市場・数値に出典または仮説ラベルがある

## プレゼン

- [ ] コンセプト → 実現方法 → 詳細の順で説明できる
- [ ] 「なぜなら」「詳しくは」「具体的には」の接続文がある
- [ ] 説明を省いた細部もQ&A用に一言で答えられる
- [ ] 図解がコンセプトやシステムの理解を補助している
- [ ] 制限時間を計測し、必要な回数のリハーサルをしている

## UXと品質

- [ ] 初回プレイの理解順序が設計されている
- [ ] 中断、保存、復帰、離脱時の扱いがある
- [ ] アクセシビリティ上の主要な配慮がある
- [ ] エッジケースがプレイヤー体験を壊さない
- [ ] 文書内に相互に矛盾するルールがない
